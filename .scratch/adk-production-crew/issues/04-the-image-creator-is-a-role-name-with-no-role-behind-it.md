# 04: The Image Creator is a role name with no role behind it

**What to build:** The agent half of image creation. Something that reads *one* bounded
unresolved visual task and decides whether to request generation for it. Today the decision is a
`for` loop, and `CrewRole.IMAGE_CREATOR_AGENT` labels events no agent produced.

## The gap

> **The Image Creator is an agent paired with a tool.** The agent interprets one bounded
> unresolved visual task and may request generation. The tool owns provider access, credentials,
> prompt derivation, job lifecycle, budget accounting, binary validation, storage, and digesting.
> (spec.md:255)

The tool half is complete and correct. `derive_generation_request`, the job lifecycle, the grant
ledger, digesting, candidate promotion, the `identityKey`-before-wording rule — all present, all
tested, and the deterministic-prompt guarantee is real.

The agent half is a loop. `ClientProductionAdapter` walks the compiler's `ASSET_PLACEHOLDER`
worklist (`services/agents/src/vox_crew/recorded.py:230-300`), derives a request for every
requirement, and starts a job for each. Nothing interprets a task; nothing declines one. The
phase event is attributed to `CrewRole.IMAGE_CREATOR_AGENT` regardless.

## Why this is a ticket and not a patch

**It is not obvious the agent should exist, and the honest version of this ticket says so.**
Every decision worth making here, the spec has already assigned elsewhere:

- The worklist is the compiler's `ASSET_PLACEHOLDER` findings, and spec.md:252 forbids a second
  list. The agent does not choose *what* to work on.
- The prompt is derived deterministically from the `AssetRequirement`, aspect ratio, closed
  treatment vocabulary and palette, and spec.md:258-261 forbids the Image Creator adding style
  prose. The agent does not choose *what to ask for*.
- Cache, repository library, placeholder, candidate, acceptance and failure decisions
  "do not belong to a model" (spec.md:250). The agent does not choose *what to do with the result*.

What is left for it to interpret is genuinely narrow: whether a requirement is worth generating
at all, and whether two requirements are the same subject when `identityKey` has not already said
so — and the second is explicitly *"a VideoPlan finding, not permission for the generator to
guess equivalence"* (spec.md:263). So the candidate scope is roughly one judgement: *this
placeholder does not need a generated image*.

That may still be worth having. It is also small enough that "the loop is the role, and the role
name is wrong" is a legitimate outcome of this ticket. Decide which, and if it is the second,
rename the role rather than leaving a name that describes something that does not exist.

**And it spends.** Every generation is authorised money. An agent that can decide *not* to
generate saves it; an agent that can decide to generate one the loop would have skipped spends it,
and no policy field names that authority today.

## Not in scope

Moving generated bytes or credentials to the agent side. ADR-0007 puts the provider call, its
credentials and its network access on the Production service, and the dead `GoogleImagenAdapter`
that sat on this side has been removed for that reason. Whatever this role becomes, it requests
generation through the published Production commands and never makes the call.

**Status:** done

## What was built, and what was decided

**The role should exist, narrowly.** The alternative — renaming `IMAGE_CREATOR_AGENT` to describe
the loop — was rejected because there is one real judgement in the phase: a placeholder can be an
editorial need for an image, or something a scene carries perfectly well without one, and
generating for the second spends money to make the film slightly worse. Nothing else in the phase
is the model's, and the `ImageCreator` protocol is written to withhold the rest.

`ImageCreator.needs_image(requirement)` is asked about **one** requirement and answers a boolean.
It derives no prompt, sees no other requirement, and reaches no provider. `AdkImageCreator`
implements it; an unreadable answer means *yes*, because a Run that silently skipped a needed
image would produce a film with a hole no finding names.

- **Asked once per requirement per Run.** Only where a requirement has no job yet, and declines
  and approvals are both recorded in the checkpoint, so a resumed Run does not spend a model call
  re-deciding. The decision reaches crew-state and tool-call evidence, and the phase outcome counts
  both requested and declined requirements.
- **Recorded runs do not install it.** A rehearsal that asked a model whether to skip work would
  stop replaying the recording it exists to replay.

- [x] It is decided, and argued in writing, whether an Image Creator agent should exist at all
- [~] If it should not: `CrewRole.IMAGE_CREATOR_AGENT` is renamed to describe the deterministic step that is actually there — not applicable; the role exists, so the name is now accurate.
- [x] If it should: it interprets exactly one bounded task per invocation, never the worklist
- [x] It cannot add style prose, and the derived-prompt guarantee is asserted unchanged
- [x] It cannot invent identity equivalence that `identityKey` did not state
- [x] Cache, library, placeholder, acceptance and failure decisions stay outside the model
- [x] Any authority to spend, or to decline to spend, is named by something an operator sets
- [x] The provider call and its credentials stay on the Production service

## Comments

**2026-09-07 — two boxes above were ticked before they held; both now do.**

*"It interprets exactly one bounded task per invocation, never the worklist."* `AdkImageCreator`
held one `AdkJsonRole`, and `AdkJsonRole.ask` cached its session id after the first call. The
payload was one requirement; the *context* was every requirement judged before it, so requirement
*N* was decided in a conversation holding 1..*N-1*. `AdkJsonRole` now takes `remembers_turns`, and
the Image Creator is built with `remembers_turns=False`, so each judgement opens its own session.
The roles whose turns are meant to build on one another keep the shared session they had.

*"Any authority to spend, or to decline to spend, is named by something an operator sets."* The
role was installed on `live_models` alone. That is an operator field, but it is the wrong one:
what this role decides is image spend, and an operator who authorised image generation had no
field that said a model could withhold it. It is now installed only when `policy.images` is live
as well — asking is a model call, and what it decides is image money, so both fields have to
allow it.
