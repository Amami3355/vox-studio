# The cloud Run, 2026-09-05

Ticket 09's own rule: *"A failure at any seam is the ticket's output, not a reason to patch and
re-run silently. Nine parts, first integration; something will be wrong. What it was and where it
was is worth as much as the success."* This file is that output. It is written as the Run
proceeds rather than reconstructed afterwards.

Spend and the "not evidenced" list were both written before anything started, in
[`cloud-proof-sheet.md`](cloud-proof-sheet.md), committed as `45535bd`.

## What the Run is

- **Brief:** `walk-31`'s, which has been produced locally before, so the topology is the only
  variable — the ticket's own reasoning for reusing a Brief.
- **Plan:** handed with `--plan`, not authored by a model. The ticket says the question is
  *whether the topology works rather than whether the crew can author something novel*, and a
  handed plan makes the Run reproducible and free of a second variable. **This is a deliberate
  cut and it means "the crew authored a plan against the remote service" is not evidenced by this
  Run.** It is named here rather than left to be inferred from the command line.
- **Work root:** a local directory holding `request.json` and `plan.json` and **no `vox.exe`**.
  The absence is the point: it is what makes "no launcher in the path" an observation rather than
  an assertion. The network client never opens the directory at all.
- **Transport:** SSH local forward, `18080 -> 127.0.0.1:8080` on the instance.

## The five isolation checks

Three from inside the tunnel, two from outside, exactly as the ticket requires — because from
outside nothing connects at all and the inside three would pass vacuously.

| Check | Where | Result |
|---|---|---|
| Unauthenticated request refused | inside the tunnel | **refused** — socket closed, no status code |
| Request with a bad body MAC refused | inside the tunnel | **refused** — socket closed |
| Replayed request refused | inside the tunnel | **first admitted (200), second refused** |
| VM has no external address | outside | **no external address** — `accessConfigs` empty |
| Crew identity cannot read a production secret | outside | **cannot** — see the qualification below |

**The replay check is the one that carries the most information**, and not for the reason it was
written. The first send came back **200 with a MAC that verified**. That means the Python
client's canonicalisation and the real TypeScript host agreed on the signing text — **the first
time the two implementations have ever spoken.** Until today that rested on a recorded vector and
a Python stub reimplementation of the boundary, which cannot catch a shape both Python halves get
wrong. It is no longer an unverified claim.

**The crew-identity check is an IAM-policy check, not a live denial.** All five production secrets
are bound to `vox-production` alone; `vox-crew` holds `VOX_CREW_MODEL_KEY` and nothing else, and
has no project-level role that would grant more. That evidences *the binding*. It does not
evidence a runtime refusal, and this file does not claim it does.

**The firewall criterion needs rewording, because as written it is not true.** Ticket 09 asks that
"the firewall admits nothing on the service's port". `vox-deny-all-ingress` denies `0.0.0.0/0` and
`vox-allow-iap-ssh` admits only `tcp:22` from the IAP range — but `default-allow-internal` admits
`tcp:0-65535` from `10.128.0.0/9`. **What actually keeps the service unreachable is that it binds
`127.0.0.1`, not that the firewall stops anyone.** With one instance in the project nothing can
exercise the gap, but the sentence and the mechanism disagree, and the mechanism is the one that
would still hold if a second instance were ever added. It is recorded as a finding, not a pass.

Corroborating this: `gcloud compute start-iap-tunnel` to port 8080 fails with
`4003: failed to connect to backend`. That is the correct behaviour and it is why the route is an
SSH local forward.

## Three seam defects, in the order they were found

### 1. The crew CLI cannot write its own output on Windows

`--discovery-only` fetched all six contract projections over the socket and then **died encoding
them to stdout**: `UnicodeEncodeError: 'charmap' codec can't encode character '→'`. The
teaching surface contains characters the Windows default code page has no room for, and
`_verbatim` in `cli.py` reconfigures the stream's *newline* handling but not its *encoding*.

This matters more than it looks. By the day-one cut the crew is the operator's local process on a
Windows machine, so this is on the delivery path, not a developer inconvenience. Worked around
with `PYTHONIOENCODING=utf-8`, which is an environment change rather than a code change — ticket
09 does not get to fix it, and the fix belongs to whichever ticket owns the crew CLI.

It is also the **third** encoding-on-Windows finding this phase: the `gcloud` metadata read-back
that appeared 15 bytes short with eight `?` in it was the same family, and so was the run before.

### 2. The Run store directory was never created, and the boot check could not see it

`run.init` failed with `ENOENT` in three seconds. The path was redacted in the envelope by the
sanitiser, and the service logs nothing about it — the error travels only in the envelope, so the
container logs said `ready` and nothing else. Tracing it in source: `withTransient` in
`payload-surface.ts` stages the init payload at `join(this.runsRoot, '.inbox-<id>.json')`, and
`VOX_RUNS_ROOT` is `/var/lib/vox/runs`. **The volume was fresh — it held `lost+found` and nothing
else. Neither `runs/` nor `ledger/` existed, and nothing in the boot path creates them.**

**`assertWritesLandOnVolume` passed at boot on this volume.** It verifies that writes land on the
disk rather than on the container's ephemeral filesystem, which is a true and useful thing, and it
is *not* the same question as whether the Run store exists. So the deployment came up green and
the first Run died. This is the project's own recurring shape — a check that cannot observe what a
reader assumes it observes — and it belongs to ticket 07.

Fixed by provisioning, not by code: `mkdir -p` plus `chmod 700` on `runs/` and `ledger/`.

### 3. The deployed image predates the route the Run needs

After the directories existed, `run.init`, `run.validate` and `run.preflight` **all succeeded over
the socket**. A Run exists on the instance — `e47463eb-9216-402b-bfc3-4d850111d935`, stage
`preflighted`, with a published preflight-report descriptor. The crew then failed reading that
artifact back: `Production did not answer /artifact at 127.0.0.1:18080`.

Both halves agree on the artifact signing text (`VOX-IPC-ARTIFACT-REQUEST-1`, the same six
length-prefixed fields) and on the schema, so the MAC was not the problem. The problem is simpler
and worse: **the running image does not have the route.** The shipped
`/app/packages/production/src/ipc/network-host.ts` is dated **Sep 2 22:15**, is 7,582 bytes, and
contains neither `PRODUCTION_ARTIFACT_PATH` nor `serveArtifact`. The route landed in `c5a3922` on
the 5th. The deployed digest `sha256:99c160c5…` is three days older than the code that needs it.

So `handle` fell through to `IPC_ROUTE_UNKNOWN` and destroyed the socket — which is the boundary
behaving exactly as designed, refusing without giving a reason, and which is why this took source
reading rather than a log line to find.

**This is ticket 07's deploy half, and it is what ticket 09 was actually blocked on.** The image
has to be rebuilt from current `HEAD` and pushed before the read-back can work at all.

## Preflight's own report

`CALIBRATION_MISSING`, as the empty volume predicted. Preflight is advisory and did not block:
`findingCount: 0`, and the report names its own limitation — *"Only compilation against a verified
Take is authoritative."* The local `walk-31` Run had a seeded calibration store, so **this is a
real difference between the local and cloud Runs** and is enumerated here rather than glossed.

## The tunnel cannot carry a render, and that is the phase's real finding

**Measured, not inferred, and the container was proved healthy across every attempt** —
`RestartCount 0`, `OOMKilled=false`, `NRestarts=0`, uptime unbroken.

- Attempt 1, through the tunnel: client failed at **181 s**.
- Attempt 2, through the tunnel: client failed at **137 s**.
- Attempt 3, from **inside the container over loopback**: answered in **1 s**.

The client's own timeout is `DEFAULT_TIMEOUT_SECONDS = 1800.0`, so none of these was a timeout.
The tunnel was confirmed **down** by a socket probe after each failure. This is the carried
"tunnel under a three-minute render" claim, and the answer is that **it does not hold**. Every
short request works over it perfectly; a long one does not.

**The second attempt's render actually succeeded.** The preview's mtime is **15:24**, inside that
attempt, and receipt `…006-run-render.json` was written. The client sat until 15:25:57 waiting for
a response that a dead tunnel could never deliver. **The failure was entirely in the return path.**
The third call found the work done and reused it, writing receipt `…007`.

There are therefore **seven receipts and two of them are `run-render`** — one for the render that
did the work and one for the reuse. No take was spent twice: `newTakesUsed` is 1 throughout.

**A correction this file owes.** After attempt 1 this document recorded that no render receipt
existed and read that as the render having failed — true of attempt 1, but attempt 2 then
succeeded server-side and its client-side symptom was attributed to the wrong cause. The render
was never the problem. The receipt chain was right; the reading of it was premature.

**The recovery was deliberately not the crew CLI.** Re-running it would have called `run.init`,
opening a fresh Run with its own take budget and recording a **second paid take** for a Run whose
take was already bound. `status` then `render` against the existing Run id spends nothing, and
`status` is the cheap probe the skill names: a stage coming back proves the ledger and the signing
key both verify.

## The render envelope is smaller than ticket 11 measured

Ticket 11 measured **178 s** under a two-vCPU cap. This render completed in **well under a minute**
on the same machine type. The figure is recorded as an observation on one brief, not as a
retirement of ticket 11's — an eight-scene brief and this one are not the same work.

## Wall time

Brief submitted 15:15:09Z, preview in hand 15:29:40Z: **14 minutes 31 seconds**, of which roughly
nine minutes were the two tunnel failures and the recovery. The productive path — `init` through
`render` — was about **75 seconds**, plus a ten-second artifact fetch.

## Boot, and two questions it closed

The instance was stopped and started to apply the new `user-data`. **Boot to service-ready: 95
seconds**, including a fresh 515 MB image pull.

- **The disk survived as the intended disk.** `ledger/`, `runs/` and `lost+found` all present after
  the cycle, with `run-75db826a380a` still in place from before it. Ticket 07 has carried this as an
  open question since 2026-09-03; it now has an observation.
- **The env fetch survived a second reboot**, this time on a `user-data` payload rendered by hand
  outside the wizard. A malformed payload would have presented as a box that boots and never serves.

**`systemctl is-active` is not a readiness check for this service.** The unit reports `active` the
moment `docker run` is launched — before the image is pulled and long before the port is bound. A
wait loop polling it returned in 53 seconds on a box with no container running. The honest signal
is the socket. This is the same shape the phase keeps producing: a check that is green for a state
weaker than its reader assumes.

## Spend

**One take, as authorised and as capped.** `newTakesUsed: 1`, `maxNewTakes: 1`, 1,289 characters of
narration across 12 segments, `eleven_v3`. The two tunnel failures cost wall time only — no take
was re-spent, because run state on disk is intact and `render` reuses what `record` already paid
for. Compute: one `e2-standard-2` in `europe-west1-c` for the session, plus one 515 MB image push
to Artifact Registry. **No currency figure is stated: no sanctioned source has delivered a rate,
and this project does not answer cost questions from training data.**
